#### R1 — P2: idle outcome/protection polling repeatedly traverses all retained history under the writer fence

**Primary location:** `src/quantbot/paper_core/outcomes.py:641` (`BEGIN IMMEDIATE` at 644 and all ENTRY lots at 647–655). Related hot paths: `outcomes.py:407`, `479`, `524`, `588`; `guardian.py:213`, `305`, `442`; `store.py:198`; `roles.py:99`; `send_guard.py:188`; `trader.py:303`.

**Trigger and effect:** Retain completed trades, as the user explicitly requested, and continue ordinary 15-second role polling. `process_outcomes` re-resolves every historical lot even when its source evidence and current outcome have not changed. For each closed lot, terminal evidence deserializes the entire broker-source table for each order; resolution reads all qualifying certification documents, all guardian receipts, all current costs and all outcome revisions. Only after that work does the current-outcome-ID equality check skip an unchanged write. The entire pass holds `BEGIN IMMEDIATE`. Both guardian and outcomes execute this path. The guardian also traverses closed entries and enters their exit-reservation transaction before discovering zero remaining quantity.

This is a concrete multiplicative hot path, not a request for generic optimization. In the accepted populated-v34 fixture there are 40 closed lots, 242 broker-source documents, 123 guardian receipts and 80 outcome revisions. Its 80 closed orders alone cause 19,360 BrokerEvent validations per unchanged outcome pass. Certification reads add per-document SQL queries. Guardian receipts and certifications continue accumulating with elapsed polling time even if no further trades occur; the runtime acknowledges at both guardian-cycle start and role-cycle completion. Separately, `ledger` rebuilds the full intent list with database lookups inside each fill iteration, producing fill-count × intent-count lookups whenever current cash is derived. Current-entry receipt selection still deserializes the complete receipt history despite the bounded role-heartbeat pointer.

As retained history grows, unrelated historical work lengthens writer exclusion and delays current guardian/outcome progress and final claims. The frozen 50-trade witness already spends 8.797 seconds on guardian plus durable outcomes against its 10-second test bound; it does not establish sustained operation after days of polling. I did not measure a particular production failure day or claim an observed 15-second breach. The missing bound and repeated work are directly visible in the executable path and conflict with the intended continuously retained history and bounded protection cadence.

**Minimal repair:** Make normal outcome polling select new/changed or explicitly pending lots, with durable bounded catch-up for late revisions and restart; resolve historical source references through indexed identities rather than rescan every payload for every lot. Keep closed lots out of ordinary guardian exit work. Use the current guardian receipt/reference for current readiness and retain exact historical receipts for retrospective joins. Build the intent/client lookup once per ledger derivation rather than once per fill. Preserve immutable history, cost/quarantine invalidation and same-ID unknown-order recovery; do not solve this by deleting history or relaxing current authority. A focused retained-history/idle-poll regression should show that unchanged old lots do not consume growing writer work and that an old late fee still causes the required revision, while a current owned exit progresses. No broad benchmark project is requested.

**Explicitly closed concern:** The anti-join in `guardian.py:162` is correct. `core_round_trips.id` is the lot ID (`outcomes.py:673–680`); the content-addressed RoundTrip ID belongs to `core_outcome_revisions` and `core_outcome_index.outcome_id`. It is not a lot-ID-versus-document-ID bug. That correct anti-join only bounds acknowledgement plan membership; it does not bound the other paths above.

#### R3 — P2: the durable entry fence has no supported audited resume operation

**Primary location:** `src/quantbot/paper_core/authority.py:261–280` and `__main__.py:40–51`. Runbook: `docs/evidence/paper-core/m6/README.md:98`.

**Trigger and effect:** The operator uses the documented `fence` command for model or executable recovery. `runtime_objections` then correctly returns `CORE_ENTRY_FENCED`. `RESUME_ENTRY` exists only as an allowed RuntimeEvent literal; no producer, CLI command or supported procedure appends it. Restart, model rollback, removal of `--entry-disabled`, and fresh reconciliation cannot clear the durable fence. The runbook explicitly postpones resume to a later implementation/review.

The result is a one-way supported operational command. It falls short of the explicit manual-pause contract (“durable until an explicit audited resume using fresh readiness”) and means completing the documented recovery cannot restore normal entries without bespoke database manipulation or new code. Automatic clearance would be wrong; absence of an authorized clearance path is also wrong.

**Minimal repair:** Add an explicit exact-current-commission/fence resume operation that appends an audited event under the existing writer fence after fresh readiness and unresolved-submission checks. Preserve all prior fence/stop events and do not clear the separate legacy/manual stop or unrelated quarantine. Refuse stale expected fence/commission and ambiguous claims. Exercise fence → continued owned exit/outcomes → refused stale resume → fresh explicit resume → new eligible claim. Document its concrete approval artifact and command.
